# 系统技术架构设计

## 1. 设计状态与依据

本文档是阶段 3 的技术架构基线，依据 `docs/data-eda-report.md` 和 `docs/requirements-v1.md`，不代表预测模型或预算目标函数已经确定。

架构必须适应以下已验证事实：

- 微信账单有 2,445 条有效记录、51 个完整周和 11 个完整月，适合单机处理。
- 周度消费变异系数为 1.44，预测需要简单模型、滚动回测和版本记录。
- 转账、退款、红包、充值和提现不能仅凭金额方向解释。
- 规则分类后“其他消费”仍占净消费 49.6%，分类必须允许用户修正。
- V1 是个人或少量用户、本地开发优先的本科毕业设计，不需要分布式系统。

## 2. 技术栈重新评估

| 层面 | 选择 | 是否 V1 必需 | 选择理由 |
| --- | --- | --- | --- |
| 前端 | Vue 3 | 是，Web 阶段 | 组件化、生态成熟，适合表单和分析页面。阶段 3 不创建页面。 |
| UI | Element Plus | 是，Web 阶段 | 覆盖上传、表格、表单和反馈组件，减少非研究性 UI 工作。 |
| 图表 | ECharts | 是，Web 阶段 | 适合周/月趋势、分类占比、预算与实际对比。 |
| API | Python + FastAPI | 是 | 与数据科学代码同语言；类型化请求、OpenAPI 和错误处理适合本科项目。 |
| ORM/迁移 | SQLAlchemy 2.x + Alembic | 是，数据管道阶段引入 | 隔离 SQLite 方言，保留迁移到 MySQL/PostgreSQL 的可能；不建立通用仓储框架。 |
| 数据处理 | Pandas + NumPy | 是 | 适合约万行级账单清洗、聚合和特征构造。Pandas 只在分析/导入层使用。 |
| 预测 | statsmodels | 后续按实验引入 | 支持指数平滑、Holt 和低阶 ARIMA；符合可解释性要求。 |
| 预测 | scikit-learn | 后续按实验引入 | 用于少量滞后特征线性模型、指标和可复现验证；不是所有路径的强依赖。 |
| 优化 | SciPy 优先 | 后续按模型引入 | 当前候选目标和约束可用常规数值优化表达，部署轻量。 |
| 优化 | CVXPY 备选 | 非默认 | 只有在最终模型能明确写成凸优化且其约束表达显著更清晰时使用。 |
| 数据库 | SQLite | 是 | 当前规模、并发和部署目标足够；数据库访问通过 SQLAlchemy，避免业务代码依赖 SQLite 特性。 |

## 3. SQLite 与 MySQL 比较

| 维度 | SQLite | MySQL | 阶段 3 判断 |
| --- | --- | --- | --- |
| 开发复杂度 | 单文件、无需独立服务 | 需要服务、用户、端口和权限配置 | SQLite 更符合本地优先 |
| 部署复杂度 | 可随应用部署和备份 | 需安装、监控和维护数据库服务 | SQLite 明显更低 |
| 当前业务需要 | 足够支持少量用户和万行级账单 | 并发能力过剩 | 当前不需要 MySQL |
| 事务与约束 | 满足 V1；写并发有限 | 更强并发和运维工具 | V1 无高写并发 |
| 迁移成本 | ORM、标准 SQL 和迁移脚本可控制 | 目标数据库 | 保持方言中立可降低成本 |
| 答辩解释 | 与规模匹配，容易说明取舍 | 容易被追问为何增加复杂度 | SQLite 更合理 |

最终选择：**V1 使用 SQLite**。只有出现多用户并发写入、独立数据库服务部署、远程运维或更强权限隔离的真实需求时再迁移。迁移不是 V1 功能。

迁移约束：

- 表名、字段名和约束使用标准 SQL 可表达形式。
- 业务层不直接调用 SQLite 专有函数。
- 通过 SQLAlchemy 会话和仓储协议访问数据。
- 使用 Alembic 管理结构变更，不手工修改生产数据库。
- 金额使用整数最小货币单位，不依赖数据库小数实现差异。
- JSON 字段只保存非核心、可解释的版本参数或诊断；核心关系必须结构化。

## 4. 总体分层

```text
Vue 3 + Element Plus + ECharts
            │ HTTP/JSON
            ▼
FastAPI 接口层（参数校验、认证边界、响应映射）
            ▼
业务服务层（用例编排、事务、权限、版本切换）
      ┌─────┼──────────┬──────────┐
      ▼     ▼          ▼          ▼
  分析模块  预测模块    优化模块    滚动再规划模块
      ▲     ▲          ▲          ▲
      └─────┴──── 领域契约 ───────┘
            ▼
仓储接口 / 数据访问层（SQLAlchemy）
            ▼
SQLite

独立导入链：私有源文件 → Source Parser → 标准候选记录
                         → Cleaning/Normalization → 导入服务 → Transactions
```

## 5. 核心模块边界

| 模块 | 责任 | 明确不负责 |
| --- | --- | --- |
| `api` | HTTP 参数校验、状态码、DTO 映射 | 不执行 Pandas、模型训练或 SQL 拼接 |
| `services` | 导入、分析、目标、预算和再规划用例编排；事务边界 | 不包含模型数学细节 |
| `parsers` | 识别来源格式并生成源无关候选记录 | 不直接写数据库、不返回 Web 响应 |
| `cleaning` | 字段校验、金额/时间规范、状态和资金流归一化 | 不决定预算或模型 |
| `analytics` | 从标准化交易生成日/周/月聚合和特征 | 不读取 Excel、不处理 HTTP |
| `forecasting` | 接收周度历史契约，输出带版本的预测结果 | 不查询网页请求、不直接提交数据库事务 |
| `optimization` | 可行性判断、预算策略和解释信息 | 不读取 Excel、不修改历史交易 |
| `replanning` | 锁定历史、组合事件与实际值、调用预测/优化生成新版本 | 不覆盖旧预算 |
| `repositories` | 领域对象的查询和持久化协议 | 不承载业务决策或模型公式 |
| `models` | SQLAlchemy 持久化模型 | 不作为 API 请求/响应对象直接暴露 |
| `domain` | 金额、枚举、周期和算法输入输出契约 | 不依赖 FastAPI、Pandas 或 SQLAlchemy |

依赖方向必须从外层指向内层：API 可以调用服务，服务可以调用领域接口和仓储；领域层不得反向依赖 API、ORM 或具体 Excel 格式。

## 6. 主要业务数据流

### 6.1 账单导入

```text
私有上传文件
  → 创建 ImportBatch（不保存本地完整路径）
  → SourceParser 识别表头和源字段
  → Cleaning/Normalization 转换金额、时间、状态、资金流
  → 生成来源记录指纹
  → 同源重复检查 + 跨源候选匹配
  → 用户确认必要的分类/匹配
  → Transaction 持久化
```

解析失败只在批次错误摘要中保存行号、错误代码和字段名，不保存交易对象、账号或完整备注。

### 6.2 分析与预测

```text
Transaction 查询
  → 按资金流口径过滤
  → 用户时区下的日/周/月聚合
  → WeeklyActual DTO
  → WeeklyForecaster 接口
  → PredictionRun + WeeklyPrediction
```

预测器接收已聚合、去标识的历史数据，不接收数据库会话或 HTTP 请求。

### 6.3 目标、预算与再规划

```text
SavingGoal + FinancialSnapshot + IncomeAssumption
  + BudgetConstraint + WeeklyPrediction
  → FeasibilityEvaluator
  → BudgetOptimizer
  → BudgetPlan(version N) + BudgetPlanItem

FinancialEvent + 实际消费 + BudgetPlan(version N)
  → Replanner（锁定已结束周）
  → BudgetPlan(version N+1, parent=N)
```

目标不可行是合法业务结果，必须保存诊断和建议，不以异常代替。

## 7. 时间与周口径

- 用户表保存 IANA 时区，V1 默认 `Asia/Shanghai`。
- 源账单的无时区时间先按导入批次的来源时区解释，再转换为 UTC 持久化。
- 交易、导入和生成时间存 UTC；前端按用户时区显示。
- 业务周固定为用户本地时间的周一 00:00 至下周一 00:00（左闭右开）。
- 周预测和预算项保存本地 `week_start` 日期；不保存易产生跨年歧义的 `week_number`。
- 月份、星期和是否周末从交易时间与用户时区计算，不在交易表冗余保存。
- 所有分析、预测和预算共用一个 `CalendarPolicy`，禁止各模块自行定义周边界。

## 8. 金额规范

- 领域层和数据库统一使用整数最小货币单位，字段后缀为 `_minor`；人民币 1 元等于 100 分。
- 每个金额对象同时带 ISO 4217 币种代码，V1 只允许 `CNY`，但结构不写死人民币符号。
- API 不接收或返回二进制浮点金额；使用整数分。前端展示时格式化为元。
- 导入时使用 `Decimal` 解析源金额，并按明确舍入规则一次性转换为整数分。
- 模型内部允许使用浮点矩阵计算，但进入预算、储蓄和持久化边界时必须量化为整数分，并记录舍入策略。

## 9. 隐私与安全边界

- 真实文件只存在私有上传区，数据库不保存本地完整路径。
- 默认不长期保存真实商户、交易对象、账号、银行卡号、商品明细或详细备注。
- 重复与内部转账匹配需要身份线索时，仅保存带应用密钥的不可逆 HMAC 指纹。
- 原始交易号不直接保存；保存来源记录 HMAC 用于幂等。
- 日志只记录批次 ID、计数、错误码和匿名实体 ID。
- 数据库文件、上传文件、备份和导出默认加入 Git 忽略规则。
- 用户可见的简短事件说明是可选字段，需长度限制和隐私提示；算法不依赖该文本。

## 10. 部署与演进

V1 采用单体模块化应用：一个 FastAPI 服务、一个 Vue 前端和一个 SQLite 数据库。模块化单体足以隔离职责，也便于答辩演示和本地复现。

以下需求出现后才评估 MySQL/PostgreSQL：

- 多用户持续并发写入；
- 多实例后端共享数据库；
- 远程备份、审计或权限隔离成为正式要求；
- SQLite 锁竞争经过测量成为瓶颈。

不提前引入微服务、消息队列或分布式任务平台。耗时模型训练若后续确有需要，优先增加同进程后台任务或简单作业表。

## 11. 阶段 4 实现核对

阶段 4 按本架构落地，没有改变技术栈或层级边界：Pandas 仅在 `WechatBillParser` 读取工作簿；来源 DTO 经独立标准化模块变为统一交易草稿；业务服务编排 ImportBatch 和仓储；SQLAlchemy 模型与 Alembic 负责 SQLite。解析器没有 SQL，ORM 没有微信中文字段，金额和时间规则由公共工具集中实现。

当前只实现导入链需要的六个实体，没有提前创建预测、目标或预算 ORM 表。后续迁移按阶段 3 的领域设计逐步增加，避免一次建立大量尚未使用的表。

## 12. 阶段9 Web集成核对

阶段9落地为模块化单体：`backend.app.main` 创建FastAPI应用，`api/routes.py`承担请求验证与权限边界，`services/web_finance.py`只做HTTP/ORM到阶段5—8契约的适配。预测、优化和replan仍调用既有服务，没有复制到Router或Vue。

Vue采用按页面懒加载，统一API客户端、金额格式器、空状态组件和ECharts封装。所有长期状态保存于SQLite；浏览器刷新不会成为计划丢失的原因。认证仅增加可空的 `users.password_hash`，兼容早期本地分析用户。
