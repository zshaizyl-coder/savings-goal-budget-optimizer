# 阶段 9.5 Web 用户体验审计

审计日期：2026-10-14。审计范围为阶段 9 已实现的 Vue 页面、FastAPI 接口及首次使用主流程；不评价或修改阶段 6—10 的算法结论。

## 结论

核心业务能力已经连通，但此前的信息架构以“功能模块”为中心，新用户进入后缺少连续任务提示。最明显的问题不是功能缺失，而是下一步不明确、技术术语暴露过多、空状态和结果页缺少行动入口。阶段 9.5 采用唯一主流程：

> 导入账单 → 确认数据质量 → 查看消费分析 → 设置储蓄目标与预算底线 → 生成并确认预算 → 按周执行 → 财务变化时重新规划

消费基线预测作为生成预算的解释性支撑，不再要求用户把它理解为一个独立的建模任务；分类人工审核是提高分类预算质量的可选步骤，不阻断总消费分析。

## 页面问题与修正

| 页面 | 审计发现 | 阶段 9.5 修正 |
| --- | --- | --- |
| 首页 | 八张同权卡片信息过载，缺少完成进度与主按钮 | 增加动态流程进度、当前任务和唯一主操作；有计划后才突出执行状态 |
| 账单 | 导入统计、技术状态、OTHER 审核和逐笔记录挤在同一层 | 导入结果分为“结果 / 数据质量 / 下一步”；分类审核折叠为可选改进 |
| 消费分析 | 图表有数据但缺少“这说明什么” | 增加统计口径、阅读提示及设置目标入口 |
| 预测 | “周度预测、模型、置信区间”对普通用户过于技术化 | 主标题改为“消费基线预测”，将方法和区间解释放入折叠详情；购物明确低可信度 |
| 储蓄目标 | 收入、最低预算、固定和可调整程度解释不足 | 使用生活化说明、输入提示和分级文案；目标保存后明确进入预算生成 |
| 预算计划 | 模式只给名称；结果先展示技术指标，激活含义不清 | 平衡模式默认推荐；候选、查看、确认激活三段式；优先解释可行性和调整风险 |
| 动态调整 | 事件表单位于执行反馈之前，用户不清楚何时需要操作 | 周度执行状态前置；使用“记录财务变化 → 预览影响 → 确认新计划”流程 |
| 历史方案 | Plan、status 等英文状态直接暴露，缺少版本原因 | 中文化状态，区分初始计划和因财务变化生成的新版本 |
| 全局导航 | 页面按技术模块平铺 | 分为“开始规划、执行与调整、记录”三组，预测标为辅助信息 |

## 跨页面一致性问题

- 空数据时必须告诉用户缺少什么以及去哪里补齐，禁止只显示空白图表。
- 金额统一显示人民币元，日期统一显示本地日期，内部枚举不直接展示。
- `OTHER` 统一显示为“其他 / 待确认消费”；A/B/C 统一显示为“优先确认 / 建议确认 / 可暂时保留”。这些是审核顺序，不代表消费重要性。
- 请求失败沿用统一安全错误，不展示堆栈、SQL 或模型内部异常。
- 预算候选不会自动生效；重新规划预览也不会覆盖旧方案，必须由用户确认。
- 1366px 与 1920px 桌面宽度保留内容最大宽度；窄屏折叠侧栏并改为横向顶部导航入口。

## 验收场景

1. 新用户直接进入目标、预算或调整页时，能看到前置条件和返回入口。
2. 导入模拟账单后，能够从导入结果连续进入消费分析、目标、预算并激活方案。
3. 已激活方案发生模拟财务变化后，能够先预览差异，再确认生成新版本；旧版本仍可查看。
4. 刷新页面后依赖数据库的状态不丢失，页面无控制台错误。
