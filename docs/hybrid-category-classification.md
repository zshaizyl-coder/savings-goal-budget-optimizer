# 混合交易分类设计（阶段 5.5）

## 目标

降低“其他 / 未分类”对分类预算分析的影响，但不以猜测替代真实类别。分类优先级为：用户确认类别、用户个人规则、通用语义规则、模型候选、OTHER。

## 三层流程

1. 通用规则只使用可解释的行业语义与公共商户别名；模糊平台、个人姓名和二维码个人收款保持 OTHER。
2. 对仍为 OTHER 的 `merchant_consumption`，可选调用大模型生成结构化候选。模型只接收脱敏短文本、金额区间、时段区间、周末标记和重复频次区间；不发送完整交易时间、精确金额、账号或持久化商户原文。
3. 所有模型结果必须人工接受或拒绝。接受后可选择仅修正当前交易，或建立仅在本机有效的匿名商户指纹规则；原始来源类别不被覆盖。

时间（例如晚餐时段）只能作为弱证据，不能单独判定餐饮。二维码支付、群收款默认不发送到远程模型。

## 真实数据验证（仅聚合）

在同一份本地真实微信账单上，核心消费共 1,470 笔、毛额 42,328.74 元。阶段 4 规则的 OTHER 为 1,044 笔（71.0%）、21,139.89 元（49.9%）。扩展后规则模拟重分类为 578 笔（39.3%）、4,680.95 元（11.1%）。

剩余 OTHER 中，456 笔（2,937.99 元）为商户消费，可进入模型候选队列；121 笔（1,722.96 元）为二维码支付，默认仅人工确认。剩余 OTHER 的中位金额为 1.30 元，前 20 个匿名商户组占其金额约 69.2%，适合优先批量审核。

上述比例是覆盖率，不是自动分类准确率。阶段 6 仍以总消费预测为主；类别预测和预算前，必须抽样审核规则与模型候选的实际正确性。

## 数据与隐私

- 只保存不可逆商户指纹、类别、规则来源、模型/提示词版本、置信度与证据代码。
- 不保存模型提示词、模型原始响应、完整商户名、交易备注、账号或支付单号。
- OpenAI Responses 接口采用 JSON Schema 结构化输出和 `store=false`；是否发送任何账单文本必须由用户在本地显式开启。
- OpenAI API 默认不用于训练模型，但官方文档说明默认滥用监控日志可能保留最多 30 天；因此该功能必须保持可选且采用数据最小化。

## 验收边界

模型仅是候选器，不是类别真值，也不进入消费预测模型。系统在无 API 密钥、无网络或用户未授权时仍可使用规则与人工确认流程。

## DeepSeek 候选分类器

- 默认关闭；只有本地 `.env` 同时配置开关和 API Key 后才可使用。
- 使用 DeepSeek 官方 OpenAI 兼容端点 `https://api.deepseek.com/chat/completions`，模型名可配置，当前默认 `deepseek-flash`。
- 按 A/B/C 审核优先级批量生成候选，每次最多 20 个商户组；发送前 Web 页面显示隐私确认。
- 请求只包含脱敏商户/说明短文本、金额区间、时段区间、周末标记、重复频次区间和商户形态；不发送精确金额、完整时间、账号和交易单号。
- 个人姓名/弱语义二维码由 `is_cloud_eligible` 在请求前拦截。时段或金额单独支持具体类别时，后端拒绝该结果。
- 数据库只保存模型名、提示词版本、候选类别、置信度和枚举证据代码，不保存提示词、原始响应或商户文本。

### 公共品牌识别与可选联网证据

- `transaction-category-deepseek-v2` 不再要求模型对所有未见名称机械保守，而是允许将广为人知的公共品牌知识作为 `counterparty_semantics`；明确茶饮品牌可候选为餐饮，明确美妆/精品零售品牌可候选为购物。
- 模糊平台、个人姓名、纯缩写和个人二维码仍不得强制猜测。更积极指“充分利用明确证据”，不表示追求 OTHER 为零。
- DeepSeek 普通 Chat API 自身不提供自动网页搜索。系统可选在调用 DeepSeek 前使用 Brave Search 查询公开商户资料，再把最多三条、总长不超过 600 字的公开摘要作为 `public_web_evidence` 交给模型。
- 搜索请求只含脱敏商户短名称和通用检索词，不含金额、时间、频率、账号、备注或用户标识；搜索摘要不入库、不写日志。搜索失败时自动退回 DeepSeek 品牌常识，不影响批次其余项目。
- 本地 `.env` 同时设置 `MERCHANT_SEARCH_ENABLED=true` 和 `BRAVE_SEARCH_API_KEY` 后才启用公开检索。API Key 只保存在本地，不得提交 Git。
- 茶宜乐与 THE COLORIST/调色师作为可公开核验的品牌别名纳入规则 v4；这类确定性规则优先于远程模型，减少重复调用成本。

真实 API 连通性先用虚构商户验证成功。随后对新年度账单的 10 个 A 级组执行一次受控试验：3 组因隐私/语义规则未发送，7 组生成待确认候选（购物1、餐饮2、交通1、居住1、保留OTHER 2）。该结果只证明接口可用和候选覆盖情况，在用户审核前不代表准确率。

## 阶段 5.6 补充

二维码记录不再被一概排除，而是先区分商户形态与个人/弱语义形态。只有商户形态可在用户授权后进入远程模型候选队列；任何候选仍须人工确认。明确行业语义由本地规则直接处理，时间与金额只用于弱提示和审核排序。

人工审核后的真实数据上，规则 v3 又安全识别 13 笔，OTHER 金额占比由 5.39% 降至 5.16%。剩余记录采用 ABC/Pareto 财务影响分级，不追求 OTHER 为零。完整结果见 `docs/qr-context-classification.md`。
