# V1 需求规格（冻结基线）

## 1. 文档状态

- 版本：V1 planning baseline
- 冻结日期：2026-10-12
- 依据：真实微信账单 EDA，2,445 条有效记录、51 个完整周、11 个完整自然月。
- 变更规则：本文件冻结的是 V1 范围和业务边界，不冻结最终预测模型、优化目标函数及权重。后续若真实多源数据或实验推翻假设，必须记录变更原因、影响和验证结果。

## 2. EDA 对需求的约束

1. 周度总消费不存在零周，但变异系数为 1.44，预测必须以短期滚动、基线比较和不确定性表达为主。
2. 四个高异常周贡献完整周净消费的 36.9%，系统必须区分真实现金流和“正常习惯”估计，并保留大额事件反馈。
3. 微信没有可靠的生活消费类别字段，规则分类后“其他消费”仍占净金额 49.6%。V1 必须允许用户确认和修正类别，不得把关键词分类当作事实。
4. “餐饮、购物”当前满足初步单独建模覆盖条件；“其他消费”虽然覆盖充足但含义异质，应先重分类，无法拆分的部分并入总量预测。其他稀疏类别使用规则、合并或总量分配，不强行训练独立模型。
5. 当前微信外部收入候选只有 22 条，不能从微信账单推断完整收入；收入和当前存款必须支持用户输入。
6. 转账、红包、充值、提现和退款需要显式资金流类型，不能只按收支符号判断消费或收入。

## 3. V1 用户与部署边界

- 目标用户：单个个人用户，本地或单机演示部署。
- 核心目标：基于用户自己的历史数据生成可解释的短期消费预测和储蓄目标预算计划。
- 数据边界：V1 的已验证导入源为微信 Excel；支付宝和银行卡属于后续增强。
- 财务边界：系统是个人预算研究原型，不提供投资、信贷、税务或专业财务建议。
- 隐私边界：真实账单只存放在本地私有目录或私有数据库，不进入 Git、公开测试、README 或明细日志。

## 4. MVP 必须实现

### 4.1 数据导入与标准化

| ID | 需求 | V1 验收要点 |
| --- | --- | --- |
| FR-D01 | 微信账单导入 | 自动识别说明行与真实表头；校验必要字段；返回聚合导入结果和可理解错误。 |
| FR-D02 | 统一交易结构 | 标准化时间、金额、方向、状态、来源、资金流类型、类别、批次和源记录标识。 |
| FR-D03 | 清洗与去重 | 处理空值、类型错误、重复源记录、状态归一化和金额精度；保留数据质量统计。 |
| FR-D04 | 资金流识别 | 至少区分核心消费、消费退款、外部收入候选、转账、转账退款、红包、红包退款、充值/提现和其他特殊交易。 |
| FR-D05 | 退款处理 | 保存消费毛额、退款额和净额；不得把退款计作新收入，也不得无痕删除原交易。 |
| FR-D06 | 类别映射与修正 | 提供通用规则初始分类、未分类/其他队列和用户修改能力；修改不覆盖原始来源字段。 |
| FR-D07 | 隐私保护 | 普通日志和页面错误不显示交易对象、完整账号、交易单号或备注；测试只用模拟/脱敏数据。 |

### 4.2 消费分析

| ID | 需求 | V1 验收要点 |
| --- | --- | --- |
| FR-A01 | 日度序列 | 按统一净消费口径生成连续日序列并补齐无交易日为 0。 |
| FR-A02 | 周度分析 | 周一至周日聚合；区分完整周和边界部分周；输出均值、中位数、标准差、CV、分位数和极值。 |
| FR-A03 | 月度汇总 | 按自然月汇总毛额、退款和净额；标记部分月，避免与完整月直接比较。 |
| FR-A04 | 分类分析 | 展示金额、频次、占比、活跃周和波动；显式标记分类为系统建议或用户确认。 |
| FR-A05 | 异常与大额提示 | 使用可解释统计阈值标记异常周/大额记录；系统只能称为统计异常，是否计划外由用户确认。 |
| FR-A06 | 时间规律 | 展示工作日/周末差异、月份差异和趋势；不凭一年数据声称稳定年度季节性。 |
| FR-A07 | 数据覆盖说明 | 页面明确当前已导入的数据源和覆盖区间，防止把微信消费误解为全部个人消费。 |

### 4.3 周度消费预测

| ID | 需求 | V1 验收要点 |
| --- | --- | --- |
| FR-P01 | 总消费预测 | 以完整周总净消费为首要预测对象。 |
| FR-P02 | 预测跨度 | 1 周为主要结果，2 周为辅助结果，4 周只作为规划参考并显示更高不确定性。 |
| FR-P03 | 必备基线 | 实现历史均值和最近 4 周移动平均。 |
| FR-P04 | 候选模型 | 至少评估简单指数平滑；Holt、低阶 ARIMA、少量滞后线性回归仅在滚动验证中有依据时保留。 |
| FR-P05 | 类别预测 | 首轮只单独测试“餐饮、购物”；“其他消费”先重分类，剩余部分并入总量预测；覆盖不足的类别使用规则或总量分配。 |
| FR-P06 | 时序验证 | 使用扩展窗口或滚动窗口回测，禁止随机打乱；至少报告 MAE，并单独观察异常周误差。 |
| FR-P07 | 模型选择 | 按用户/数据集独立选参；若候选未优于基线，生产方案保留基线。 |
| FR-P08 | 月度预测汇总 | 从周度预测映射到自然月；跨月周按日历天数或经验证的日度权重分摊，不重复计入。 |

### 4.4 储蓄目标与可行性

| ID | 需求 | V1 验收要点 |
| --- | --- | --- |
| FR-G01 | 目标输入 | 当前存款、目标金额、目标日期、当前/未来收入及其生效周期。 |
| FR-G02 | 支出约束 | 用户设置固定支出、类别最低预算和调整偏好；历史分类不能自动决定“必要”。 |
| FR-G03 | 可行性判断 | 在最低支出和收入假设下先判断目标是否数学可行，再生成预算。 |
| FR-G04 | 不可行解释 | 返回“当前目标不可行”，并计算最高合理目标、收入缺口、最早完成日期及可调整约束。 |
| FR-G05 | 假设透明 | 页面显示可行性计算使用的收入、时间边界、最低预算和数据截止时间。 |

### 4.5 分类预算优化

| ID | 需求 | V1 验收要点 |
| --- | --- | --- |
| FR-B01 | 周/月预算 | 生成未来周度分类预算，并以一致规则汇总自然月预算。 |
| FR-B02 | 约束满足 | 满足储蓄目标、现金流、固定支出、类别最低预算、非负预算和用户调整意愿。 |
| FR-B03 | 习惯偏离 | 优化目标体现相对用户历史正常消费的偏离，但最终函数和权重由后续实验确定。 |
| FR-B04 | 可插拔策略 | 同一接口支持统一比例削减、历史占比分配和个性化优化三种方法。 |
| FR-B05 | 可解释输出 | 展示每类历史参考、最低值、推荐值、调整金额及触发约束，不只输出“少花多少”。 |
| FR-B06 | 不可行保护 | 不得通过突破用户最低预算或伪造未来收入生成表面可行方案。 |

### 4.6 实际反馈与滚动再规划

| ID | 需求 | V1 验收要点 |
| --- | --- | --- |
| FR-R01 | 锁定历史 | 已发生交易和已结束周期不可被预算模块修改。 |
| FR-R02 | 周度反馈 | 每周录入/导入实际消费，比较预算偏差并更新当前财务状态。 |
| FR-R03 | 事件触发 | 支持大额消费、额外收入、收入下降、目标金额/日期和最低预算变化。 |
| FR-R04 | 调整模式 | 支持储蓄目标优先、平衡调整、生活稳定优先和自定义调整程度。 |
| FR-R05 | 未来重算 | 只重算未来周、剩余月和后续月预算；重新判断目标可行性。 |
| FR-R06 | 版本追踪 | 保存计划版本、触发原因、数据截止点和算法版本，能够比较固定预算与滚动预算。 |

### 4.7 基础 Web 系统

| ID | 需求 | V1 验收要点 |
| --- | --- | --- |
| FR-W01 | 导入页 | 上传微信账单，展示聚合校验结果和隐私提示。 |
| FR-W02 | 分析页 | 展示周/月趋势、分类分布、异常提示和数据覆盖信息。 |
| FR-W03 | 预测页 | 展示模型/基线、1/2/4 周结果、误差和不确定性说明。 |
| FR-W04 | 目标与约束页 | 输入储蓄目标、收入、固定支出、最低预算和调整偏好。 |
| FR-W05 | 预算与进度页 | 展示可行性、分类预算、储蓄路径、实际偏差和计划版本。 |
| FR-W06 | 再规划交互 | 提交状态变化并显示旧计划与新计划的未来部分差异。 |

## 5. 非功能需求

- NFR-01 可复现：所有分析、预测和优化运行记录数据截止时间、参数和代码/算法版本。
- NFR-02 可解释：关键分类、排除、预测和优化结果能追溯到规则、输入和约束。
- NFR-03 隐私：真实数据不进入 Git；默认日志不记录隐私明细；删除本地数据后不保留隐蔽副本。
- NFR-04 正确性：金额采用整数分或定点数；时间周期边界有自动测试；退款与内部资金流有专项测试。
- NFR-05 可恢复：重要阶段使用独立分支和提交，`main` 保持可运行。
- NFR-06 性能：单个约 10,000 行账单的导入和基础分析应在普通个人电脑可接受时间内完成；V1 不为高并发设计。
- NFR-07 可维护：来源解析器、预测器和预算策略使用接口隔离，不能把某个真实用户金额或权重硬编码到代码。

## 6. 后续增强

- 支付宝账单解析器及字段映射。
- 银行卡流水解析器及银行格式适配。
- 跨源去重、退款关联和本人账户内部转账匹配。
- 更完整的用户分类规则与批量修正。
- 更多预测模型和预测区间方法，但只在滚动回测证明有价值时加入。
- 节假日、学期或用户事件特征。
- 更丰富的图表、导出和论文实验看板。
- 经需求验证后的多用户、认证和远程部署。

## 7. 不在 V1 范围内

- LSTM、Transformer、大语言模型或其他深度学习预测。
- Hadoop、Spark、微服务、Kubernetes、消息队列。
- 实时银行 API、自动抓取支付账户或云端账单同步。
- 自动判定某笔消费“必须”或“浪费”；必要性必须由用户决定。
- 自动识别所有本人账户间转账；V1 对无法确认的转账采用保守排除和人工核验。
- 投资组合、信贷、税务、保险或会计记账系统。
- 原生移动 App。
- 高并发 SaaS、多租户计费和企业级权限体系。
- 为显得正式而引入 MySQL；V1 默认 SQLite。
- 用 11 个完整月直接训练复杂月度预测模型。

## 8. 研究与对照实验接口

V1 数据与服务接口必须允许后续比较：

- 预测：历史均值、4 周移动平均、简单指数平滑及少量合格候选。
- 预算方法 A：统一比例削减。
- 预算方法 B：按历史消费占比分配。
- 预算方法 C：个性化动态预算优化。
- 规划机制：固定预算与滚动预算优化。

每次运行必须保存方法名称、版本、输入截止时间、目标/约束版本和聚合评价结果，不能把系统写死为单一策略。

## 9. V1 完成判定

V1 只有在以下条件同时满足时才算完成：

1. 模拟数据测试覆盖导入、退款、转账/充值排除、周边界、不可行目标和滚动锁定历史。
2. 真实微信账单能本地导入，但真实明细不进入 Git、测试或普通日志。
3. 两个基线和至少一个简单候选完成滚动回测，所有指标来自真实运行。
4. 可行与不可行目标均有自动测试和可解释输出。
5. 三种预算策略共享接口，固定/滚动机制可进行对照。
6. Web 前后端贯通导入、分析、预测、目标、预算和再规划主流程。
7. `main` 保持可运行并存在对应里程碑提交或标签。
