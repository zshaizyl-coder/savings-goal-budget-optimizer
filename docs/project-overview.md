# 项目概述与阶段 0 可行性评估

## 研究目标

系统面向个人储蓄目标，将多源账单标准化为统一交易数据，学习单个用户自身的消费特征，生成周度消费预测与分类预算方案，并在收入、支出或目标变化时仅对未来周期滚动再规划。

## 当前证据边界

- 当前工作区尚未找到指定微信账单文件。
- 下表是工程和研究方案层面的初步评估，不包含任何真实数据统计或模型效果结论。
- 风险等级会在真实 EDA 完成后复核。

## 技术可行性评估

| 评估项 | 风险 | 评估理由与建议 |
| --- | --- | --- |
| 1. 多源账单导入 | 中风险 | 微信、支付宝和银行导出格式不同，表头、交易状态、收支符号和转账语义均需适配。采用“源适配器 + 统一交易模式 + 可追溯原始字段”可实现，但必须逐源验证。 |
| 2. 微信真实账单作为核心案例数据 | 中风险 | 一年微信账单可作为真实案例，但当前文件缺失，且仅微信可能漏掉支付宝、银行卡和现金活动。它适合作为第一数据源，不等同于完整个人财务画像。 |
| 3. 一年数据进行周度分析 | 低风险 | 理论上约有 52 个周度观测，足以进行描述统计、基线和短期滚动验证；首尾不完整周、无交易周与异常周必须单独处理。 |
| 4. 周度消费预测 | 中风险 | 样本量适合简单可解释模型，但结构突变、节假日、大额偶发支出和多源缺失会降低稳定性。应以基线和滚动时序验证为核心，不承诺高精度。 |
| 5. 月度汇总 | 低风险 | 可从统一日度交易自然汇总月度实际值。预测汇总需按日历边界分配周预测，避免跨月周重复计入，不能简单把整周硬归属某月。 |
| 6. 储蓄目标可行性判断 | 低风险 | 可根据当前存款、未来净收入、剩余周期、固定支出和最低预算构造确定性约束，并输出最大可达目标、收入缺口或最早日期。未来需明确收入不确定性与日期边界。 |
| 7. 分类预算优化 | 中风险 | 约束优化可实现；难点在于最低必要消费和可调整性需要用户确认，历史消费不能自动等同于“必要”。目标函数和权重需通过实验与敏感性分析确定。 |
| 8. 滚动再规划 | 中风险 | 以已发生交易锁定、更新财务状态并重算未来预算在数学和工程上可行。需严格处理时间边界、状态版本、幂等性和不可行目标。 |
| 9. Web 系统实现难度 | 中风险 | Vue 3 + FastAPI + SQLite 足以支撑单机本科原型。文件上传、隐私保护、分析任务状态和图表联调有一定工作量，但无需微服务。 |
| 10. 作为数据科学本科毕业设计 | 低风险 | 课题覆盖真实数据清洗、EDA、特征、预测评价、数学优化、对照实验和 Web 实现，研究链条完整。主要风险是数据覆盖度与样本量，而非题目本身。 |

## 需要保留并进一步验证的问题

1. 约 52 周样本不足以支持复杂模型或可靠的长周期季节性估计，后续应限制模型复杂度和预测跨度。
2. “类别最低预算”“固定支出”“可调整支出”不能仅由交易类别自动决定，必须允许用户确认和覆盖。
3. 跨月周的预测汇总必须设计明确的分摊规则，推荐先生成日历周预测，再按天数或日度权重映射到自然月；最终方法需实验确认。
4. 单一微信数据源的预测对象应明确为“可观测的微信消费”，多源接入前不能宣称代表完整总消费。
5. 计划外大额支出应同时保留在真实现金流中，并在用于“正常消费习惯”估计时设置可解释的异常处理策略，而不是直接删除。

## 初步结论

项目方案基本可行，适合作为本科毕业设计。当前不存在已知的致命逻辑错误，但真实账单缺失阻塞了数据可用性判断、模型候选收敛和 V1 需求冻结。
