# 微信账单导入流水线（阶段 4）

## 1. 范围与边界

本阶段只实现微信 Excel 账单到统一交易表的本地数据链：解析、逐行标准化、规则分类、幂等去重、质量统计和 SQLite 持久化。支付宝、银行卡、消费预测、预算优化、Web 页面和滚动再规划均未实现。

模块边界如下：

```text
Excel -> WechatBillParser -> WechatSourceTransaction
      -> WechatTransactionNormalizer -> StandardTransactionDraft
      -> WechatImportService -> Repository -> SQLite
```

Parser 不接触数据库；Normalizer 不读取 Excel 或 ORM；Repository 不解释微信中文字段；API 未来只调用业务服务。

## 2. 已验证的真实格式

真实账单原地只读验证得到：一个 `Sheet1` 工作表、前 17 行说明、第 18 行表头，表头后 2,445 行。实际字段为：交易时间、交易类型、交易对方、商品、收/支、金额(元)、支付方式、当前状态、交易单号、商户单号、备注。

表头通过必要字段集合在前 50 行内识别，不写死为第 18 行；找不到表头或工作簿不可读为 `FATAL`。表头后的空行跳过；看似说明/合计且没有时间和金额的行作为 `WARNING` 跳过；单行金额、时间或方向错误为 `ROW_ERROR`，不会中止其他行。

来源 DTO 只在导入进程内存在，包含上述 11 个来源字段及 Excel 行号。它与长期保存的 Transaction 严格分离。

## 3. 金额和时间规则

- 金额先由 `Decimal` 解析，再转换成非负整数分；禁止 `float(text) * 100`。
- 已测试 `0.01`、`1.00`、`10`、`10.10`、`9999.99`、货币符号、空值、负数、非法文本和三位小数。
- 交易时间先按用户时区解释，当前默认 `Asia/Shanghai`，随后转换为 UTC 持久化。
- SQLite 的普通时间列不保留偏移，因此 `UTCDateTime` 类型在写入时保存无偏移 UTC，在读取时恢复带 UTC 时区的 datetime。
- 业务周始终以用户本地时间计算，周一至周日；数据库不保存 `week_number` 或 `month` 冗余列。

## 4. 资金方向与业务流

`direction` 与 `flow_type` 独立：前者只有 `inflow/outflow/neutral`，后者描述业务语义。

| 微信来源语义 | flow_type | 处理原则 |
| --- | --- | --- |
| 商户消费、扫码付款、群收款且为支出 | consumption | 进入核心消费候选 |
| 二维码收款 | income_candidate | 只作为收入候选，不直接认定为工资 |
| 商户类 `*-退款` | expense_refund | 作为负向消费，不作为收入 |
| 转账 | transfer | 保留，暂不计入日常消费 |
| 转账退款 | transfer | 由 `source_type_code` 与退款状态区分 |
| 红包及红包退款 | red_packet | 单独保留 |
| 零钱充值、零钱提现 | balance_transfer | 资产账户移动，不作为收入或消费 |
| 无可靠规则的来源类型 | other | 保留并产生 warning |

仅有微信数据时无法可靠判断“给别人转账”和“本人账户间转移”。因此真实验证中 `internal_transfer=0`，654 条普通转账均保留为 `transfer`；跨源数据加入后再通过 `transaction_links` 候选匹配和人工确认。

## 5. 退款与净消费

退款本身保存为独立交易，`flow_type=expense_refund`。净消费的统一规则是：

```text
消费支出贡献 = +amount_minor
消费退款贡献 = -amount_minor
其他资金流贡献 = 0
```

因此 100 元消费和 30 元退款的净贡献为 70 元，不会把退款当成新收入。系统使用相同匿名交易对象指纹、时间顺序、金额兼容和原交易退款状态进行保守关联：唯一候选才写入确认的 `refund_of` 链接并继承原消费类别；不唯一或无候选时保留退款并告警。

真实数据的 103 条消费退款中，29 条满足当前高置信自动关联条件，74 条没有被强行关联。净总消费仍可由正负流量计算，但未关联退款的类别净额需要在阶段 5 单独评估。

## 6. 同源幂等和重叠导入

幂等分两级：

1. 文件 SHA-256 相同：仍创建 ImportBatch 作为一次可审计尝试，但状态为 `duplicate_file`，新增交易为 0。
2. 行级来源指纹相同：优先使用平台交易号生成带应用密钥的 HMAC；没有来源 ID 时使用时间、金额、方向、类型、商户订单号和匿名对象组合。数据库唯一约束为 `(user_id, source, source_record_fingerprint)`。

不同来源 ID 但时间、金额、方向和业务流完全相同的记录不会自动删除，而是两条都入库，并创建 `possible_duplicate/pending` 候选链接。模拟重叠文件测试中，两条来源 ID 相同的记录被跳过，两个新记录入库，其中一个同时间同金额的不同来源 ID 记录进入人工确认候选。

未来跨平台重复和内部转账继续复用 `transaction_links`，不会为支付宝或银行卡另建交易表。

## 7. 类别映射

统一类别为阶段 3 确定的适中集合。规则集中在 `category_rules.py` 并带 `wechat-category-v1` 版本：

- 先根据安全的来源类型代码确定是否具有消费分类意义；
- 消费类记录仅在内存中使用交易类型、对象和商品文本执行阶段 1 已验证的通用关键词规则；
- 数据库只保存统一类别和非敏感的原始类型标签，不保存被命中的商户或商品文本；
- 无可靠规则时进入 `other`，以后用户修正类别优先于自动类别。

真实核心消费中，`other` 占交易笔数 71.0%，占消费毛额 49.9%。金额占比与阶段 1 的“其他消费约占一半”一致，说明主要问题是微信缺少统一生活类别，而不是解析失败。本阶段不使用文本机器学习，也不扩大猜测规则来人为降低该比例。

## 8. ImportBatch 与质量报告

每次导入都记录来源、文件类型、文件不可逆指纹、开始/完成时间、状态、总行数、解析数、新增数、重复数、失败数、警告数、时间范围和解析器版本。错误摘要只保存行号、字段名和错误码，不保存源单元格内容。

返回的结构化质量报告还包含：未知类型、消费退款、普通转账、转账退款、内部转账、余额转移、退款关联、可能重复、未分类笔数/金额比例和 flow_type 分布。它可在后续 Web 页面直接展示。

## 9. 隐私策略

- 真实 Excel 始终在私有附件位置原地只读，不复制到仓库。
- Transaction 不保存交易对象、商品描述、备注、支付方式、平台交易号或商户单号。
- 幂等、对象和支付账户线索只保存带密钥的 HMAC。
- CLI 和质量报告只输出聚合计数、时间范围和错误码。
- 测试只依赖 `data/sample/` 下的完全模拟账单；自动测试检查源码不含真实附件路径或真实文件日期标识。
- `.env`、私有目录和 SQLite 文件继续由 `.gitignore` 排除。

## 10. 数据库迁移与本地运行

阶段 4 首迁移为 `0001_stage4`，建立 `users`、`import_batches`、`categories`、`category_mappings`、`transactions` 和 `transaction_links`。全新数据库必须先执行：

```powershell
$env:DATABASE_URL = "sqlite:///data/private/app.sqlite3"
.venv\Scripts\alembic.exe upgrade head
```

导入 CLI 要求通过环境变量提供不可为空的 `TRANSACTION_FINGERPRINT_KEY`。脚本不自动打印原始交易内容。真实运行密钥不得提交 Git。

## 11. 验证结果与当前限制

- 自动化测试：30 项全部通过，包括迁移 downgrade/upgrade、表头、金额、时间、方向、业务流、分类、退款、未知类型、行级容错、幂等、重叠导入和隐私字段检查。
- 真实账单：2,445/2,445 行解析并首次入库；失败 0；第二和第三次分别新增 0、重复 2,445。
- 性能：模拟持久化 1,000、5,000、10,000 条分别约 0.068、0.278、0.571 秒。本结果只用于确认不存在灾难性瓶颈，不作为跨机器性能承诺。
- 限制：仅有微信账单时无法确认内部转账；退款自动关联率有限；分类没有人工标注准确率；外部收入候选不是完整收入。这些限制必须由后续数据源或用户确认解决。
